# US091 - View Remote Access Logs

## 1. Analysis

### User Story

As Administrator, I want to view the logs stored at the Remote Accesses Logging Server.

### Dependency

This user story extends US090. The same application continues to receive remote-access events
through UDP and persist them in `remote-access.log`, while also exposing an HTTP visualization
layer for standard web browsers.

### Acceptance Criteria

1. The Remote Access Logging Server contains an HTTP server.
2. A page presents the last recorded events.
3. A page presents the currently active remote users.
4. Both pages represent the current server state.
5. AJAX updates the data without reloading either page.

---

## 2. Design

### Main Components

- `RemoteAccessLoggingServer`
  - Starts the UDP receiver and embedded HTTP server.
  - Persists each valid incoming datagram and forwards it to the in-memory store.

- `RemoteAccessLogStore`
  - Parses the semicolon-separated format defined by US090.
  - Keeps the 100 most recent valid events, newest first.
  - Reconstructs state from the existing log file at startup.
  - Tracks active sessions in a thread-safe way.

- `RemoteAccessHttpServer`
  - Uses the Java 17 built-in `HttpServer`.
  - Serves HTML status pages and JSON API endpoints.
  - Requires no additional web dependency.

### Active Session Rules

A session is identified by:

- username;
- client IP;
- client port;
- service identifier.

`LOGIN_SUCCESS` adds an active session. `LOGOUT` and `DISCONNECT` remove the matching session.
Failed logins and successful business operations do not change active-session state.

---

## 3. HTTP Interface

| Path | Content |
| --- | --- |
| `/` | Navigation page |
| `/events` | Last recorded events page |
| `/active-users` | Currently active users page |
| `/api/events` | Recent events in JSON |
| `/api/active-users` | Active sessions in JSON |

The pages execute `fetch()` every two seconds. The returned JSON is used to replace only the
table rows, so the browser document is not reloaded.

The interface escapes JSON values on the server and inserts values using DOM `textContent` on
the client, preventing log values from being interpreted as HTML.

---

## 4. Configuration

Default ports:

- UDP logging port: `9000`
- HTTP visualization port: `8081`

Command:

```bash
./run-remote-access-logging-server.sh [udpPort] [logFile] [httpPort]
```

Windows:

```bat
run-remote-access-logging-server.bat [udpPort] [logFile] [httpPort]
```

The HTTP port can also be configured with:

- system property `remote.access.logging.server.httpPort`;
- environment variable `REMOTE_ACCESS_LOGGING_SERVER_HTTP_PORT`.

## 5. Automated Tests

`RemoteAccessLogStoreTest` verifies:

- newest-first event ordering;
- maximum event-list size;
- login and logout session transitions;
- reconstruction from an existing file;
- rejection of malformed log lines.

`RemoteAccessHttpServerTest` verifies:

- both HTML pages are available;
- each page contains its AJAX request;
- automatic updates are scheduled;
- both JSON endpoints return current data;
- an active user disappears after a disconnect without restarting the HTTP server.

Execution:

```bash
mvn test
```

## 6. Manual Tests

### Preparation

Start the logging server:

```bash
./run-remote-access-logging-server.sh 9000 remote-access.log 8081
```

Open:

- `http://localhost:8081/events`
- `http://localhost:8081/active-users`

Start the remote access server and client using the US090 validation procedure.

### Scenario 1 - Existing Events

1. Place valid US090 entries in `remote-access.log`.
2. Start the logging server.
3. Open `/events`.

Expected result:

- Existing entries are displayed newest first.
- Up to 100 events are presented.

### Scenario 2 - New Event Without Page Reload

1. Keep `/events` open.
2. Perform a remote login or successful operation.
3. Do not reload the browser page.

Expected result:

- Within two seconds, the new event appears at the top.
- The page status displays a new update time.

### Scenario 3 - Active Login

1. Keep `/active-users` open.
2. Log in through a remote access client.
3. Keep the client connected.

Expected result:

- Within two seconds, the user appears with IP, port, service, and connection time.

### Scenario 4 - Logout or Disconnect

1. With the user visible on `/active-users`, perform `LOGOUT` or close the client.
2. Do not reload the browser page.

Expected result:

- Within two seconds, the matching session disappears.
- The corresponding `LOGOUT` or `DISCONNECT` remains visible on `/events`.

### Scenario 5 - Independent Browser Clients

1. Open both pages in different browsers or tabs.
2. Generate remote access events.

Expected result:

- Both clients update independently.
- No manual refresh is required.

---

## 7. Result

The Remote Access Logging Server now provides the two required browser status pages, backed by
live JSON endpoints and AJAX polling. Existing US090 persistence and UDP reception remain in
place, and the visualization state is rebuilt from the stored log whenever the application starts.
