# US102 - Detect aircraft safety violations in real time

## 1. Analysis

### User Story

As a simulation system, I want to continuously monitor aircraft positions for overlaps so that I can identify and report safety violations.

### Acceptance Criteria Addressed

1. The system detects when two or more aircraft may eventually violate safety rules.
2. Upon detecting a violation, the system logs the event and notifies the involved aircraft via signals.
3. Each flight process handles the received signal and notifies the user with a message.
4. When a flight process receives a `SIGUSR1` (violation detected), it blocks other signals while handling it.
5. The system allows early termination if safety violations exceed a predefined threshold by sending termination signals to aircraft.
6. Flight processes properly handle termination signals and perform any necessary cleanup.

## 2. Design

### Main Process

Added responsibilities compared to US101:

- initialize the `SafetyLog` before launching flight processes;
- after consolidating all `PositionUpdate` messages for a given time step, invoke the safety monitor to scan the current state of the `PositionTracker`;
- send `SIGUSR1` to each flight process involved in a detected violation;
- accumulate detected events in the `SafetyLog` and enforce the early-termination threshold (`VIOLATION_THRESHOLD`);
- on threshold exceeded or interruption (`SIGINT`/`SIGTERM`), send `SIGTERM` to active flights and close all sync pipes to release any child blocked on `read`;
- print the safety log summary at the end of the simulation;
- include the full list of violations in the final report file.

### Flight Process (`flight_process.c`)

Added responsibilities compared to US101:

- register a `SIGUSR1` handler with `sigfillset(sa_mask)` so that all other signals are blocked during the handler execution, as required by the acceptance criteria;
- in the handler, use only async-signal-safe functions (`write`) to notify the user that a violation was reported by ATC;
- the startup signal was moved to `SIGUSR2` to reserve `SIGUSR1` exclusively for safety notifications;
- append the PID to the `flight_id` sent in each `PositionUpdate`, ensuring that multiple flights using the same plan are tracked as distinct entries in the `PositionTracker` — a prerequisite for correct pairwise comparison in the violation detector.

### Safety Monitor Module (`safety_monitor.c`)

Responsibilities:

- maintain a `SafetyLog` aggregating all detected events during the simulation;
- on each simulation step, evaluate every flight in `RUNNING` state whose latest update corresponds to the current step;
- detect **altitude violations** when a flight's current altitude is below `safety_min_alt_m`;
- detect **separation violations** for every pair of flights whose horizontal distance (haversine, in nautical miles) is below `safety_min_sep_nm` and whose vertical distance is below `safety_min_alt_m`;
- record each violation as a structured event (type, timestamp, involved flights/PIDs, distance/altitude);
- notify the involved flight processes by sending `SIGUSR1` via `kill`;
- expose a textual summary of all logged events.

## 3. Main Structures

- `ViolationType`: enumeration distinguishing `VIOLATION_SEPARATION` from `VIOLATION_ALTITUDE`.
- `SafetyViolation`: a single detected event — time step, type, identifiers and PIDs of involved flights, distance (for separation) or altitude (for altitude violations).
- `SafetyLog`: fixed-size buffer of up to `MAX_VIOLATIONS` events plus a `total_detected` counter that may exceed the buffer size, used by the threshold mechanism.

## 4. Implementation Decisions

- **Haversine formula** is used for horizontal distance because flight coordinates are geographic (latitude/longitude); Euclidean distance would produce significant errors over large areas.
- **Separation criterion** requires *both* horizontal proximity (`< safety_min_sep_nm`) *and* vertical proximity (`< safety_min_alt_m`), aligned with standard aviation practice where vertical separation alone can satisfy safety rules even at close horizontal distance.
- The **detector runs in the parent process between simulation steps**, after all `PositionUpdate` messages for the current step have been consolidated in the `PositionTracker`. This guarantees a coherent snapshot and avoids race conditions, as the detection is fully single-threaded.
- **`SIGUSR1` is reserved exclusively for violation notifications** to comply with the US102 acceptance criteria. The startup signal was reassigned to `SIGUSR2`.
- The signal handler in each flight process uses `sigfillset(sa_mask)` (excluding `SIGKILL` and `SIGSTOP`, which cannot be blocked) to ensure that no other signal interrupts the handler — directly satisfying acceptance criterion 4.
- The handler only calls `write()` (async-signal-safe) and sets a `volatile sig_atomic_t` flag, following the safe pattern of "notify, not perform".
- The **early-termination threshold** (`VIOLATION_THRESHOLD = 10`) is checked after each detection cycle. When exceeded, the parent sets `stop_requested = 1`, exits the main loop, closes all sync pipes (forcing `read()` in children to return EOF) and sends `SIGTERM` to active flights. This combination guarantees timely cleanup even for children blocked waiting for the next-step command.
- Appending the **PID to the `flight_id`** in `PositionUpdate` was necessary because multiple flights using the same plan share the same plan-level identifier; without disambiguation, the `PositionTracker` would merge them into a single entry, breaking pairwise violation detection.

## 5. Assumed Limitations

This implementation evaluates violations on a per-step basis using the consolidated state of the `PositionTracker`; it does not perform predictive analysis on intermediate sub-step positions. Weather influence on the safety thresholds is out of scope for this US — it would require integration with the weather data subsystem (planned for later sprints with shared memory in US105+). The threshold value is a compile-time constant; a future improvement could make it configurable via command-line arguments. Step-by-step time progression and synchronization belong to US103, which is already partially integrated through the sync pipes used during cleanup.
