# US108 - Sincronizar a progressão da simulação utilizando semáforos

## 1. Objetivo

O objetivo desta user story é garantir a progressão sincronizada passo a passo da simulação utilizando semáforos POSIX.

Cada processo de voo deve aguardar autorização explícita do processo pai antes de avançar para o próximo timestep da simulação. Isto garante que todos os processos de voo progridem de forma sincronizada e que o processo pai mantém controlo total sobre o fluxo da simulação.

---

## 2. Contexto

Esta user story estende o mecanismo de sincronização previamente introduzido na US103.

O mecanismo anterior baseado em pipes de sincronização foi substituído por sincronização baseada em semáforos para melhorar a coordenação entre o processo pai e os processos filhos, mantendo simultaneamente uma progressão determinística dos timesteps.

O mecanismo de comunicação de atualizações permanece inalterado e continua a utilizar pipes para enviar atualizações de posição dos processos filhos para o processo pai.

---

## 3. Dependências

* US101: Capturar e processar movimentos de voo
* US103: Sincronizar a execução dos voos com um timestep
* US105: Inicializar ambiente híbrido de simulação com memória partilhada

---

## 4. Solução Implementada

A lógica de sincronização foi redesenhada de forma que:

* os pipes de atualização continuam a ser utilizados para transmitir posições dos voos dos processos filhos para o processo pai;
* os pipes de sincronização foram removidos;
* a memória partilhada armazena os semáforos de sincronização;
* o processo pai controla explicitamente a progressão de cada timestep da simulação.

### Elementos Adicionados à Memória Partilhada

A estrutura de memória partilhada foi expandida com:

```c
sem_t step_start[MAX_FLIGHTS];
int terminate;
```

### Modelo de Sincronização

Cada processo de voo:

1. Calcula o movimento para o timestep atual;
2. Envia atualizações através do pipe de atualização;
3. Aguarda autorização do processo pai;
4. Continua apenas quando o processo pai liberta o próximo timestep.

O processo pai:

1. Aguarda todas as atualizações necessárias;
2. Processa as posições das aeronaves;
3. Deteta violações de segurança;
4. Liberta o próximo timestep utilizando semáforos.

---

## 5. Fluxo de Sincronização

### Processo Filho

```text
calcular movimento
        ↓
enviar atualização ao pai
        ↓
aguardar semáforo
        ↓
receber autorização
        ↓
continuar próximo timestep
```

### Processo Pai

```text
receber atualizações
        ↓
processar posições
        ↓
detetar violações
        ↓
libertar semáforos
        ↓
próximo timestep
```

---

## 6. Detalhes de Implementação

### Sincronização dos Processos Filhos

Os processos de voo aguardam permissão antes de avançar:

```c
sem_wait(
    &shared->step_start[flight_index]);
```

A terminação também é validada após a sincronização:

```c
if (terminate_requested || shared->terminate)
{
    terminate_requested = 1;
    break;
}
```

### Sincronização do Processo Pai

O processo pai liberta os voos ativos:

```c
sem_post(
    &shared->step_start[i]);
```

### Encerramento da Simulação

Quando ocorre a terminação da simulação:

```c
shared->terminate = 1;

for (int i = 0; i < config.flight_count; ++i)
{
    sem_post(
        &shared->step_start[i]);
}
```

Isto garante que os processos filhos bloqueados são libertados e terminam corretamente.

## 8. Testes Realizados

### Teste 1 - Execução concorrente com múltiplos voos

Configuração:

* 2 voos concorrentes;
* área entre latitude 39–43 e longitude -9 a -3;
* timestep = 30 segundos;
* duração total = 3600 segundos;
* altitude mínima = 300 m;
* separação mínima = 10 NM;
* limite máximo de violações = 30.

Esperado:

* os voos avançam sincronizados timestep a timestep;
* nenhum processo avança sem autorização do pai;
* o sistema suporta múltiplos processos concorrentes.

Resultado:

* aprovado.

Observações:

* ambos os voos completaram a execução;
* cada voo gerou 121 updates;
* o sistema processou todos os timesteps sem deadlocks nem bloqueios;
* o estado final da simulação foi `PASS`.

---

### Teste 2 - Controlo centralizado do timestep

Esperado:

* apenas o processo pai autoriza a progressão da simulação.

Resultado:

* aprovado.

Observações:

* os processos filho permaneceram bloqueados em `sem_wait()` até receberem autorização;
* a progressão ocorreu em lockstep durante toda a execução.

---

### Teste 3 - Integração com validação de segurança

Esperado:

* a sincronização não interfere com a deteção de violações.

Resultado:

* aprovado.

Observações:

* foram detetadas 2 violações de altitude no instante inicial;
* o threshold máximo permitido não foi ultrapassado;
* a simulação terminou corretamente com resultado `PASS`.

---

## 9. Conclusão

O mecanismo de sincronização foi migrado de sincronização baseada em pipes para sincronização baseada em semáforos.

Esta implementação garante progressão determinística dos timesteps, previne condições de corrida durante o avanço da simulação e centraliza o controlo da simulação no processo pai, preservando simultaneamente os mecanismos existentes de comunicação para transmissão de atualizações.
