# US106 - Function-Specific Threads Implementation in the Parent Process

## 1. Objective
Add dedicated, decoupled execution threads to the simulation controller parent process—specifically for real-time safety violation detection and asynchronous report generation—ensuring that each core system functionality operates concurrently, securely, and independently without blocking the simulation clock execution.

---

## 2. Requirements Implemented
The implementation includes:
- **Multithreaded Simulation Controller:** Parent process creates and coordinates specialized lifecycle workers.
- **Dedicated Safety Detection Thread:** Independent thread responsible for scanning shared memory snapshots for flight boundary conflicts and proximity breaches.
- **Dedicated Report Generation Thread:** Decoupled consumer thread managing persistent simulation output files and real-time stderr logs.
- **Local Synchronization Framework:** Strict internal coordination utilizing robust POSIX mutexes and condition variables.
- **Thread-Safe Data Snapshotting:** Mutual exclusion handling across shared logistics data to completely prevent race conditions between tracking data inputs and parsing threads.

---

## 3. Architecture

### Parent Process (Main Loop)
Responsibilities:
- Initialize the synchronization contexts, mutexes, and boundary variables.
- Spawn the permanent safety detection and report generation threads.
- Act as the primary step coordinator by receiving pipe outputs, writing to shared states, and updating time barriers (`steps_ready`).
- Clean up thread worker allocations and cleanly broadcast termination signals at shutdown.

### Safety Detection Thread
Responsibilities:
- Wait on local condition flags (`step_cond`) for the main loop to freeze state snapshots.
- Safely parse the shared flight entry matrices via `safety_check_shared`.
- Automatically signal the asynchronous reporting thread whenever new violations cross thresholds.
- Manage step acknowledgment counters (`steps_checked`) to unlock the simulation master clock safely.

### Report Generation Thread
Responsibilities:
- Monitor violation logs continuously by sleeping on specialized signaling conditions (`violation_cond`).
- Sequentially consume pending safety events from log histories without interrupting live tracking.
- Provide simultaneous output pipeline operations (writing to real-time `_violations.log` files and stderr diagnostics).

---

## 4. Structures Introduced

### SimulationThreadContext
Encapsulates thread coordination metadata, containing:
- Pointers to mutual tracking structures (`SharedSimulationState`, `SimulationConfig`, `SafetyLog`, `FlightRuntime`).
- **`step_mutex` & `step_cond`:** Thread-safe state barriers between the master controller and safety checkers.
- **`report_mutex` & `violation_cond`:** Producer-consumer messaging tools mapping safety breaches to live logs.
- Execution trackers (`steps_ready`, `steps_checked`, `violations_reported`).
- **`stop`:** Global volatile execution flag triggering uniform thread exit strategies.
- File configurations mapping destination paths for persistent data (`realtime_log_path`).

---

## 5. Synchronization Model

| Mechanism | Utilization |
| :--- | :--- |
| `step_mutex` | Protects boundary integers (`steps_ready` / `steps_checked`) during step increments. |
| `step_cond` | Blocks parent loop until safety inspection ends, and vice-versa. |
| `report_mutex` | Guards concurrent access to safety log arrays and mutation indexes. |
| `violation_cond` | Awakes the report engine thread instantly when a new hazard is logged. |
| `shared->mutex` | Standard shared memory semaphore maintaining atomic snapshots of flying vectors. |

---

## 6. Compatibility
The US106 thread model seamlessly integrates with preceding milestones:
- **US100 / US101 / US102:** Retains pipe data streams and handles automated asynchronous `SIGUSR1` alarms targeting failing child tasks.
- **US103 / US105:** Coordinates clock ticks seamlessly with active process tracking matrices, updating centralized logging layers safely.
- **Threshold Terminations:** Main processes successfully detect early crash limits parsed by safety workers and terminate cleanly.

## 7. Tests Executed

### Unit Testing (`test_simulation_threads`)
- **Initialization/Destruction Tests:** Ensures local contexts properly launch threads with zeroed counters.
- **Thread Signaling Simulations:** Spawns mock consumer/producer workers using `SimulationThreadContext` to guarantee conditional variable blocks wake up reliably upon step updates.

### Integration Testing
- **Execution Lifecycle Checks:** Verifies simulation runs successfully under high loads, generating accurate `simulation_report.txt` data.
- **Real-Time Data Streams:** Validates that `_violations.log` records anomalies concurrently, proving that file operations execute independently from flight path calculations.

---

## 8. Result
The architecture successfully partitions computational concerns in the parent process. Critical flight boundary audits and heavy physical I/O disk writes now run on dedicated threads, removing latency from the core loop and providing a highly scalable structure for the overall simulation engine.
